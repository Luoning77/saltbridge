# 性能与资源管理

2026-10-28：对照官方指南 https://saltplayer.com/workshop/performance.html 调整。

## 当前行为

- `CoreRegistry.start()` 只安排后台初始化。读取配置、创建数据目录、初始化令牌和写配对文件均在后台运行；停用会使尚未完成的启动失效。启动提示表示“正在后台启动”，不表示 HTTP 已就绪。
- 播放进度事件更新状态，不逐次输出日志。诊断日志使用 256 条有界队列；后台每秒批量刷新，达到约 2 MiB 后轮转，仅保留当前文件和一份备份。日志队列满时允许丢弃日志，不能阻塞播放事件。
- 停用不再等待事件线程 200ms，也不在调用线程等待日志写盘；HTTP 仍同步关闭以释放监听端口。
- 歌词查询队列最多 8 条，积压时保留较新的请求；执行前核对查询是否过期，完成后继续由状态引擎校验代次。
- 封面缓存同时限制为最多 8 张、总计 32 MiB，单张仍最多 16 MiB。失败记录最多 128 条，在查询时清理过期项；待处理封面最多 8 个。
- 封面提交被拒绝时清除在途标记，后续请求能够重试；清理缓存前创建的任务不能在清理后重新填充缓存。

上述上限是插件自己的保留数据/任务限制，不是播放器整个进程的内存上限；宿主返回原始大图片时也可能产生短时分配。

## 自动验证与实机验证边界

回归测试覆盖封面总字节淘汰、待处理数量、失败缓存上限、队列拒绝、清理后的迟到任务、日志关闭落盘、慢配置启动及立即停用，并保留原有 HTTP 和播放状态测试。

日志 `startup.ready` 的 `backgroundMs` 是后台初始化耗时，不是播放器总启动时间，也不是插件 `start()` 回调耗时。还需要在真实 Windows 环境测量启用前后 CPU、内存和界面响应，分别验证首次启动、再次启用、慢磁盘、大封面、快速切歌和连续启停；自动测试不能替代这些测量。

## 本地曲库能力

当前依赖 Workshop API `0.1.0-dev23` 的 `Library` 包含：

- `getAllTracks()`：一次读取 Salt Player 已导入的完整曲库。
- `getTracks(afterId, limit)`：按歌曲 ID 游标分页读取，适合游戏内列表。

这些调用需要 `LIBRARY_READ` 权限；SaltBridge 已声明此权限，但用户仍需授权。它们读取的是播放器曲库，不扫描硬盘上尚未导入的文件。

SaltBridge 新增 `/api/v1/library/tracks` 分页接口：默认每页 50 首、最多 200 首；查询等待上限 3 秒，最多 4 个待处理任务；页面缓存 10 秒、最多 8 页。不在启动时全量读取曲库。MC Mod 本次未修改；列出歌曲与点选播放是两个能力，新增后者前需另外核对播放 API。
